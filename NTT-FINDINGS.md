**Date:** 2026-10-04
**Part:** `GW1NR-LV9QN88PC6/I5` (GW1NR-9, version C)
**Tool:** Gowin `V1.9.11.03 Education`
**Host:** `fort`, working tree `/home/yoda/p2-synth/ntt`
**Oracle:** `kyber-py` 1.2.0 (`kyber_py.ml_kem.ML_KEM_768`)

One methodology per table. Every number below comes from a committed report

## 1. What was wrong

`ternary_poly_mul` does not multiply polynomials. Its own reference model,
`verify/verify_poly_mul.py`, states the computation exactly:

```python
for d in range(depth):
    for ch in range(CHANNELS):
        acc[ch] += activations[d][ch] * weights[d][ch]
```

Sixteen independent dot products. No negacyclic wraparound, no reduction
modulo X^256+1, no index exchange between lanes, no NTT. The module is a
16-lane ternary dot-product engine with a correct mod-3329 reducer attached.

It passed its testbench because the testbench checks the RTL against a
Python reimplementation of the same RTL. That is a self-consistency check,
not a correctness argument, and it is why the gap survived.

Separately, `rtl/top.v` has exactly three module instantiations — `picorv32`
and two `wb_uart` — and never instantiates the accelerator at all. The block
at `0x03000000` is four writable registers and a read mux whose
`accel_result` register is reset to zero and never driven.

## 2. The oracle

The reference model `ref/mlkem_ntt_ref.py` is validated three ways before
being used, and the RTL vectors are generated by the published
implementation rather than by the model:

| Check | Result |
|---|---|
| Twiddle table equals the published ML-KEM values | PASS (128 entries) |
| `INTT(NTT(f)) == f` over 200 random polynomials | PASS |
| NTT-domain multiply equals schoolbook negacyclic convolution | PASS, 50 pairs |
| Same, with an eta=2 secret operand | PASS, 50 pairs |
| Reference agrees with `kyber-py` forward NTT | PASS, 100 random polynomials |

The third row is the one that matters: schoolbook negacyclic convolution in
Z_3329[X]/(X^256+1) **is** the definition of the operation, so agreeing with
it is agreeing with the standard rather than with oneself.

RTL test vectors `v0..v2_{in,out}.hex` are emitted by `kyber-py`.

## 3. RTL result

`tb_mlkem_ntt` against vector 0: **PASS, 256/256 coefficients.**

Two defects were found and fixed in the process, both worth recording
because both are silent:

1. **Barrett width.** `x * BR` evaluated in a 32-bit context overflows: the
   widest operand here is 3328*3328 = 11,075,584 and BR = 5039, so the
   product needs 36 bits. The fix is a 64-bit intermediate, which widens the
   evaluation context. The repo's existing `barrett_reduce.v` gets this right
   with a 64-bit stage register; written as a one-line function it goes wrong
   without any warning. All 256 coefficients were wrong before the fix.
2. **BSRAM write mode.** Gowin's dual-port block rejects `WRITE_MODE 2'b10`
   (error PA2122). The design never reads and writes the same port in one
   cycle, so no-change semantics cost nothing. The RTL was re-verified in
   simulation after the change, before any synthesis number was taken from it.

**It fits, with room to spare.** Measured headroom before this work was 6,373
logic cells; integrating a correct NTT consumed 116 of them. The correct
implementation is roughly **50× smaller** than the incorrect one it replaces.

**Timing is the thing to watch.** 27.049 MHz against a 27 MHz constraint is
0.18% margin across 25 logic levels. The Barrett reduction is combinational
and is almost certainly the critical path. It should be pipelined before
anyone builds on this, and no claim should be made about operating above
27 MHz without re-closing.

## 5. The eta=2 question, resolved

The README states:

> The ternary decomposition of lattice coefficients maps exactly onto the
> existing `{00=0, 01=+1, 10=-1}` weight encoding.

This is false for ML-KEM-768, and the reason is more fundamental than the
three-versus-five-values arithmetic.

ML-KEM-768 has eta1 = eta2 = 2, so secret and error coefficients are drawn
from a centred binomial distribution over {−2,−1,0,+1,+2} — five values. A
ternary weight holds three. The exact distribution is P(|c| = 2) = 1/8, so
87.5% of coefficients would fit a ternary lane directly.

But ML-KEM does its polynomial multiplication **in the NTT domain**, because
that is what makes it fast. Measured over 200 secret polynomials
(`ref/eta2_cost.py` and the check in this repo's history):

| | fraction with abs(coeff) <= 1 |
|---|---|
| secret `s`, normal domain | **87.6%** |
| `NTT(s)`, NTT domain | **0.1%** |
| uniform over Z_3329, for comparison | 0.09% |

The transform destroys the small-coefficient property. In the domain where
the multiplication actually happens, there is no ternary operand to exploit.
A ternary MAC could only help a schoolbook multiply in the normal domain,
which is O(n^2) and slower than the NTT it would replace.

**Consequence.** The claim does not survive, and neither does the stronger
reading of it — that a ternary MAC accelerates ML-KEM polynomial
multiplication. What is genuinely shared between the inference and
cryptographic paths is the adder/subtractor datapath, the modular reduction
and the block memories, not the ternary encoding. The README claim is
withdrawn rather than narrowed, and the architecture claim should be restated
in those terms.

A second claim is also unsupported: **"~100× speedup over PicoRV32 software
for all Polysub operations."** There is no benchmark, no software baseline
and no log anywhere in the repo that produces this figure. It should be
measured or removed.

## 6. Hashing — the remaining scope gate

Not yet measured. What is measured is the budget left after the NTT:

| Resource | Free after the NTT system |
|---|---|
| Logic | 6,257 / 8,640 |
| Logic registers | 5,490 / 6,480 |
| BSRAM | 10 / 26 |

A Keccak-f[1600] permutation needs 1,600 registers for the state alone,
which is 29% of the free register budget, and a compact slice-serial core is
typically one to two thousand LUTs. On those figures it fits, but that is a
budget argument and not a measurement, and it is recorded here as such.
Establishing it properly needs a synthesised core.
